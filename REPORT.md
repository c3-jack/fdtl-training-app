# Week 1 Report

**The defects.** A wrong guess of four tiles was showing a hint toast ("One away!") even when only two of the four tiles actually belonged to the same category, not the three it takes to be genuinely close. Selecting five tiles was supposed to be impossible once four were already picked, but the fifth tile highlighted anyway and locked the Submit button instead of staying disabled the normal way. The color dropdown next to each category showed the wrong color name selected compared to the strip actually shown, and picking a color from the list assigned a different color than the one you clicked. Separately, the hardest (purple) category's solved banner had no text color at all, unlike the other three, which made it visually inconsistent even though nothing crashed.

**Where the agent helped, and what it got wrong.** The agent found each root cause quickly by reading the relevant function instead of guessing from symptoms, and it reproduced every defect in the browser before touching a file, which caught one mismatch early: on the first repro attempt for the one-away bug, a page scroll shifted the tile grid between a screenshot and the following clicks, so it selected the wrong four tiles (1 horror + 3 Pixar, a real near-match) instead of the intended unrelated combination, and had to redo the selection. Separately, when I asked it to confirm the new filler group title was unique, it initially only grepped the local checkout, which reflected `main`, without checking the other students' remote branches or `filler-updates` — I had to ask before it went back and searched across all of them.

**Why the guess-check fix belongs in `puzzle.ts`.** `checkGuess` in `src/lib/puzzle.ts` is the one function that classifies a guess as correct, one-away, or wrong; every caller (the play panel's submit handler) just trusts its return value and renders whatever it says. The bug was in the classification logic itself — counting 2-of-4 as one-away instead of 3-of-4 — not in how the result gets displayed, so the smallest correct fix is the one-character change inside that function. Patching it anywhere else (e.g. special-casing the toast in the component) would duplicate the classification rule and leave the actual bug in place.

**The merge conflict.** Merging `filler-updates` conflicted in `filler-groups.ts` because both branches inserted new entries at the same anchor point. I kept my own filler group and all three of the incoming branch's groups, deleting only the conflict markers, then re-ran the build to confirm nothing was left behind. Keeping just one side — either dropping the incoming three groups to make the conflict disappear, or dropping my own — would have looked like a clean resolution but would have silently destroyed real category data that other groups' work (or the shared pool) depends on.
